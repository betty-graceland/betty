# Betty — Architecture

## Why Betty

Betty is a custom autonomous personal business AI for Peter Benes — operator
of Benes The Menace™ (consulting practice), kPixies™ (performance-based Google
Ads program for brick-and-mortar retailers), and the Attention Optimization™
commercial play. She is not a generic agent template. She is a local-first
operator built to take real work — research, drafting, monitoring, analysis —
off Peter's plate without surrendering judgment, client trust, or data
sovereignty to the cloud.

The non-negotiables that shape every architectural decision below:
- **Local-first.** Data lives on the Mac Studio. Cloud calls only at the
  external action boundary.
- **Governed autonomy.** Betty does not act on external systems without
  explicit per-action evaluation by a separate Judge model.
- **Human-promoted memory.** Lessons learned do not silently become rules.
  All instruction-grade memory requires human confirmation through a
  review queue.
- **Scarce-memory discipline.** 32GB of unified memory means one big model
  resident at a time. Architecture optimizes for memory pools, not parallel
  compute.

## Hardware

- **Machine:** Mac Studio, Apple Silicon (M-series), 32GB unified memory
- **Storage:** Local SSD; no cloud-synced paths in the project tree

## The Four Planes

Betty is organized as four planes, each with a single responsibility and
minimal coupling to the others.

### Plane 1 — Ingestion (asynchronous, isolated)

Python ETL workers extract content from local sources, normalize, chunk,
embed in-process, and write to Postgres. The Actor model is never in this
loop. Embeddings are generated by `sentence-transformers` running
`nomic-embed-text` directly inside the ETL Python process — explicitly
not via Ollama — to prevent memory contention with the resident Qwen
actor.

**Sources:** Apple Mail `.emlx` files, local PDFs, local document folders.
**Sink:** Postgres `source_documents` and `source_document_chunks` tables.

### Plane 2 — Substrate (Postgres as system of record)

Single local Postgres 16 instance with pgvector 0.8.2, running in Docker
on port 5433. This is the OpenBrain. Every other plane reads from or
writes to it. No other shared state exists.

**Tables (Stage 1):**
- `schema_migrations` — migration tracking
- `source_documents` — parent records, one per ingested artifact
- `source_document_chunks` — chunk-level records with 768-dim embeddings,
  HNSW indexed for cosine similarity

**Tables (future stages, not yet built):**
- `memories` — provenance-labeled facts and rules
- `review_queue` — human-in-the-loop governance items
- `judge_decisions` — log of every Judge evaluation
- `work_records` — wrapped state machines for emails/docs (5-property pattern)
- `intent_parameters` — machine-readable business values

### Plane 3 — Cognition (Qwen Actor + OpenClaw runtime)

OpenClaw runs as the local agent gateway. Qwen 2.5 32B (4-bit quantized)
is served by Ollama at `localhost:11434` and is the **only** model Ollama
serves. The actor is constrained to an 8k context window; the Markdown OS
is sized to fit comfortably inside that budget while preserving Ollama's
prefix cache across turns.

The local reflection loop (used when the actor is stuck) invokes the same
Qwen model via a different system prompt and context bundle, exposed as a
`betty.reflect.v1` tool call. It is operationally separate but
mechanically identical to actor calls — no second resident model.

### Plane 4 — Governance (Cloud Judge + Review Queue)

At any tool call classified `reversible_write`, `external_side_effect`, or
`high_risk`, the OpenClaw `before_tool_call` hook fires the Judge adapter.
The adapter builds an Action Proposal Envelope, calls OpenBrain recall,
then calls Claude 3.5 Sonnet via Anthropic API as the Judge. Decisions are
written to `judge_decisions`. Lessons that should become future rules land
in `review_queue` for human confirmation via a localhost-only web UI.

**Cost controls (Stage 4):** hard daily spend cap, structured per-call
logging, judge never on the hot path of read-only work.

## Critical Architectural Decisions

### The Action Proposal Envelope split

Qwen emits the **semantic justification** for an action (intent,
authorization basis, evidence IDs, risk self-assessment). The adapter
adds **mechanical fields** (UUIDs, timestamps, schema versions,
checksums). The adapter validates that every evidence ID Qwen cites
resolves to a real row in OpenBrain. Hallucinated references become a
deterministic block before the Judge ever sees the envelope. This
preserves the chain of accountability — the Judge evaluates Qwen's
reasoning, not the adapter's guess at it.

### Prompt assembly for cache hits

Ollama's prefix cache invalidates the moment any byte changes in the
cached region. To preserve TTFT across turns, the prompt is assembled
in stable order: system prompt → AGENTS.md → USER.md → MEMORY.md slice
→ SKILL.md descriptors → conversation history → retrieved evidence →
current message. Markdown OS files are frozen at session start. No
timestamps or session IDs in the system prompt.

### Embedding isolation

Embeddings run in-process via `sentence-transformers`, not via Ollama.
This is non-negotiable: it prevents background ETL embedding requests
from triggering Qwen unload/reload thrash during active actor sessions.
Ollama serves exactly one model. The ETL is fully self-contained.

### Stage-locked schema

Schema tables are created only when the stage that uses them is being
built. No speculative columns, no speculative tables. Future stages
have entries in `OPEN_QUESTIONS.md`, not premature migrations.

## Build Stage Sequence

1. **Substrate** ✓ — Postgres + pgvector, schema migration system
2. **ETL Skeleton** — Python pipeline, sentence-transformers, PDF + Apple Mail extractors
3. **Local Actor** — OpenClaw + Ollama + Qwen, minimal Markdown OS, read-only conversation
4. **Judge Adapter** — `before_tool_call` hook, Anthropic API integration, single tool (draft_email)
5. **Review Queue UI** — FastAPI on 127.0.0.1, list/confirm/reject flows
6. **REVISE Loop** — structured revision reinjection
7. **Heartbeat** — launchd-triggered periodic awareness
8. **Work Records + Intent Parameters** — 5-property wrapping, operating model
9. **Reflection Loop** — invoked only when proven necessary
